# Theme system audit

Reviewed 8 September 2026 against PR #63 at `521ea782`, plus its CI assertion fixes. This is a code audit and comparison with primary documentation, not a claim of complete platform or accessibility certification. Recommendations below are proposed work.

## Assessment

API 1 provides a usable installation and distribution foundation and meaningful home customization. It does **not** yet meet the original goal of letting a theme author redesign every part of the client. Global colors and appearance are available, but replaceable structures are limited to the home hero, rank badge and ordinary media cards. Putting the editor inside Themes is the right navigation arrangement; expanding the contract and authoring tools matters more than adding another settings entry.

Already implemented: a GitHub catalog, individual HTTPS links and JSON imports, preview/cancel, offline installed designs, explicit updates, preservation of personal edits, rollback and stable home-row overrides. An optional large rank badge belongs comfortably in this system. See [THEMES.md](THEMES.md) for the implemented contract.

Efficiency and navigation assertions remain enabled.

The corrected full local suite passes: **3,920 tests passed, 7 skipped; 475 files passed, 4 skipped**. The Windows checkout needed Worker dependencies installed, as CI already does, and local LF normalization for existing source-text checks. Those setup adjustments introduce no unrelated source changes. CI on the pushed commit remains the authority for Linux and native checks.

Search/library surfaces outside that context, detail layouts, navigation, settings, specialized progress cards and player structures cannot be composed by a theme. | Introduce documented component slots with stable IDs and host-owned data/actions. | First | **Contract and authoring drift.** The catalog copies the presentation validator. Its schema generator produces listing/catalog/release schemas, but no schema for the actual package design or template tree. There is no cross-repository parity check. The catalog format guide also described outdated appearance defaults; that wording is corrected alongside this audit. | Publish one versioned contract artifact that generates runtime validation, package JSON Schema and reference documentation. | First | **Permanent interaction and recovery coverage.** The current browser fixture was temporary; the two CI failures demonstrate the fragility of source-string tests. | Next | **Editing beyond sliders.** `ThemeLayoutEditor.svelte` provides common controls and a JSON textarea. | Next | **Assets, variants and semantic styling.** Packages offer four font choices and host poster/backdrop/logo bindings. ## What established systems suggest

These are design comparisons, not features to copy wholesale:

- **Reusable components and broad surface contracts:** Kodi documents shared includes, control defaults and constants that can be reused across windows. That is a useful model for scaling beyond a separate JSON tree for every row. Izumi should expose named component slots and reusable definitions while retaining its own data/action contract. [Kodi Skinning Manual](https://kodi.wiki/view/Skinning_Manual#Includes)
- **Stable semantic hooks:** Vencord's ThemeAttributes documents explicit attributes and variables for theme authors. The relevant lesson is to maintain supported identities for components and states instead of tying themes to incidental markup. Izumi's stable row IDs are a useful start. [ThemeAttributes](https://vencord.dev/plugins/ThemeAttributes)
- **Author tools and personal overrides:** VS Code documents color customization, exporting current settings, JSON completion/color pickers and live development previews. Izumi already has preview and editable copies; package-schema completion and a proper inspector are the largest authoring omissions. [Color Theme guide](https://code.visualstudio.com/api/extension-guides/color-theme)
- **Compatibility metadata:** VS Code requires publisher and engine compatibility declarations and supports license metadata. Izumi should declare supported client versions/capabilities before theme APIs evolve independently of the catalog. [Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest)
- **Assets as part of a visual package:** Spicetify documents optional image/font assets alongside theme definitions. Izumi lacks an equivalent asset mechanism. This supports adding a constrained asset bundle, without adopting its optional JavaScript execution model. [Theme development](https://spicetify.app/docs/development/themes)
- **Responsive acceptance criteria:** W3C's reflow guidance addresses content at a width equivalent to 320 CSS pixels, including carousel panels. A 390px screenshot alone is insufficient evidence. Test zoom/reflow, text enlargement and each individual card or panel as well as the overall page. [Understanding Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## Recommended sequence

Review follow-ups from [PR 63](https://github.com/nickEatsBread/izumi/pull/63):

- Keep the catalog's validator and format documentation synchronized with the numeric display-field contract; the catalog change is tracked in [izumi-themes PR 1](https://github.com/nickEatsBread/izumi-themes/pull/1).
- Add contrast checks for template text where its foreground and background can be resolved, with visual checks for transparency and artwork. The current catalog checks structure and integrity, not rendered readability.
- Restrict theme downloads to HTTPS throughout redirects, including catalog/release documents. This needs a scoped native transport option because the shared HTTP client has other consumers; a package checksum does not authenticate a listing fetched over a downgraded connection.
- Profile dense themed grids on supported controller hardware before setting an aggregate render budget. The 96-node limit applies per template, and existing navigation assertions do not measure device performance.

1. Finish CI verification, establish the canonical schema and permanent fixture, and address the concrete interaction/recovery gaps before expanding the public contract.
2. Extend complete component families with responsive/state variants. Publish a coverage matrix so users know what a theme can change. A home preset should remain distinguishable from a theme that covers the shell and detail screens.
3. Build the visual inspector and author-defined options on that contract; add reusable components, named variants and assets. Require two substantially different example compositions as acceptance evidence for each new family.
4. Expand discovery, compatibility metadata, update review, custom catalog subscriptions and optional sync as the catalog grows.

Keep executable scripts, arbitrary HTML and unrestricted CSS outside the theme format. The missing flexibility can be added through supported declarative slots, states, assets and host callbacks. Every new surface should retain a stock fallback when a package cannot render it.
