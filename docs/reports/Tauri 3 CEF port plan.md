# Tauri 3 CEF port: phase plan

The owner approved the port after the Deck spike ([Tauri 3 CEF spike on the Steam Deck](Tauri%203%20CEF%20spike%20on%20the%20Steam%20Deck.md)). Every platform moves to Tauri 3. Linux runs the CEF runtime in offscreen mode with izumi's own compositor, and Windows (WebView2), macOS (WKWebView) and Android keep their webviews through the wry runtime. On Chromium, motion is plain CSS and scrolling is native: the WebKit workarounds are deleted, not ported.

**Branch.** `feat/tauri3-cef-linux`, cut from `origin/feat/packs` (PR #202), or from `main` once #202 merges. There is one commit series per phase. One draft PR collects the phases, and it merges only after phase 4 passes and the owner makes the phase 5 decision.

**Data migration.** The CEF build reads `engine-migration.json` from app data on first launch, restores it as an app backup (secrets included) and deletes it. Writing that file is the job of the last WebKitGTK release, which is a separate change on `main`.

**Linux release job.** `release.yml`'s `ubuntu-24.04` entry still asks `tauri-action` for the default Linux bundles. Whether the Tauri 3 alpha CLI bundles CEF into a `.deb` or AppImage is unverified; the Flatpak is the shipped Linux target either way.

## Risks

- **Alpha churn.** Tauri 3 is an alpha. Pinning exact versions in phase 1 keeps the rest of the port from moving under it.
- **Windows.** The WebView2 COM code (hole player, cookies, DevTools receiver) depends on how `with_webview` looks on the Tauri 3 wry runtime. Phase 1 settles it before anything else changes.
- **Android.** The local plugins' Kotlin side may need Tauri 3 plugin API changes, and installing on a device needs the owner.
- **Build memory.** CEF builds are heavy on this laptop. Builds run in WSL under a memory cap with `-j2`, and every one checks commit and C: free space first.
- **Shared Deck.** Other sessions use the Deck. Every launch there is asked for first.
